# 知识库维护约定

[首页](README.md)

## 一份正文，多个入口

- `docs/wiki/` 是知识库正文源，根 `llms.txt` 是简短 AI 索引；README、文档首页和排障入口只链接到这里。
- `npm run sync-plugin` 将正文复制到插件的 `skills/dsh-remote-doctor/references/wiki/`。这是构建副本，不直接编辑；插件既有 skills 分发范围会携带它。
- 本轮不创建或发布外部 GitHub Wiki。以后需要网页/Wiki 展示时，从同一来源生成，并解决链接与版本对应；不手工维护两套正文。
- 旧专题报告保留原结果与日期。不要把一次旧测试“通过”批量替换为新版本已验收。

## 新条目的最低内容

每个问题使用稳定编号，例如 KB-CONN-01；标题包含用户会搜的原词。写清：

1. 现象与影响范围。
2. 适用端、版本/能力与核对日期；区分仅源码、已发布、实装和实机。
3. 第一轮只读取什么、哪些字段能区分原因。
4. 每个分支的下一步、动作影响与授权要求。
5. 验收结果，以及仍未知时如何退出/反馈。
6. 源码/测试/专题依据，附上脱敏后的典型错误，不贴用户日志。

常见操作使用“目标 → 入口 → 前提 → 完成后核对”；不要把后端内部术语直接当成用户步骤。安全边界有变化时，同时更新 AI 指引和内置 Doctor。

## 更新与检查

- 修改实际行为时更新对应页、首页检索表和错误索引；本次新增实验性插件折叠、发布计数等尚未分发的行为，应明确标为源码基线。
- 运行文档链接/打包副本检查，并检查内置 Doctor 的相对链接能在安装包内定位。
- 改同步脚本或技能内容后运行相关回归及 `npm run sync-plugin`，确认 npm 包确实包含离线文档；无需仅为 Markdown 改动重建 APK。
- 只有用户明确要求发布时，才执行远端 Wiki 同步、提交、push、发布或替换线上资产。

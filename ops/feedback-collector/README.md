# 反馈收集器

Python 标准库服务，与客户端、网关共同完成普通反馈、可选诊断附件、中央公告和公开投票统计。

## 部署文件与核验

一起部署 `server.py`、`diagnostic-schema.json`、`public_polls.py`。白名单由根目录 `npm run sync-plugin` 生成；不要仅覆盖 `server.py`。投票模块来自现有线上服务，已纳入源码，避免更新反馈功能时丢失 `/public-polls.json`。

`GET /health` 返回 `protocol: 2`、正文/投票/请求体预算、正文摘要和诊断报告编号回执能力，以及运行进程启动时加载的源码和白名单 SHA-256。通过客户端实际 HTTPS 域名读取这些字段并与待部署文件比较，不能只看文件上传成功或服务 active。

普通反馈上限为 20000 个 UTF-16 单元，请求体上限 256 KiB；投票仍为 2000。JSONL 写入、flush 和 fsync 成功后才返回正文 `messageSha256`；保存诊断时返回 `clientDiagnosticsReceived`。客户端和网关仍需同步升级。网络结果不确定时不自动重发。

## 更新步骤

1. 先运行 `node --test tests/diagnostic-feedback.test.js` 和全量 `npm run check`。
2. 核对当前 systemd 服务的运行用户、工作目录和启动文件，记录现有 `/health`、公告文件摘要及公开投票结果。不要输出真实反馈正文或联系方式。
3. 将三份文件上传到服务目录内的独立暂存目录，逐一比较 SHA-256；校验 Python 语法、JSON 和模块导入。不要修改 `data/`。
4. 在权限为 0700 的备份目录保存当前代码、白名单（若存在）、投票模块和数据快照。用 `os.replace` 替换代码文件，再重启已确认的 `feedback-collector.service`。
5. 通过服务内部地址和客户端 HTTPS 地址读取 `/health`，确认源码/白名单摘要与限制；核对公告、投票汇总及原反馈数据。失败时恢复代码并重启，数据保持原样。
6. 用隔离网关发一条标明「验收测试」的合成反馈，检查长正文、可选诊断、网关回执与 JSONL 记录摘要。不要把 HTTP 200 当作正文和附件都已保存，也不要在结果不确定时重复提交。

公开投票只返回最新已公布投票的选择题累计数，不公开反馈记录、IP、联系方式或填空答案。回归测试同时覆盖该隐私边界和升级兼容。
